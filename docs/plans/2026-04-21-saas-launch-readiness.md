# SaaS Launch Readiness Plan

> Generated by the daily-improvement scheduled task on 2026-04-21.
> Audits ran against `main` at commit `9a39753`.

**Goal:** Close the gaps that would block Namihr from selling to paying B2B customers. No speculative features — every task either (a) protects money/data, (b) keeps the app debuggable when customers call, or (c) answers a question a procurement/security reviewer will actually ask.

**What's already planned (do NOT duplicate here):**
- `2026-04-19-pre-launch-security-hardening.md` — sanitized errors, targetPath allowlist, dashboard proxy auth, server logout, Slack OAuth state (mostly merged; only Task 7 rate-limiting remains open).
- `2026-04-20-slack-integration-hardening.md` — 13 tasks covering Slack token encryption, event dedup, HMAC-signed OAuth state, queue-based fan-out, idempotent sends. **Phase 1 of that plan is still a launch blocker** and should ship before anything below that depends on customer-facing trust (tokens in plaintext = no SOC 2, no enterprise deal).

**Launch posture decision:** The app cannot ship to paying customers until Phase 1 below is done. Everything in Phase 2 is "fix during first 60 days" — you can start selling with a short vendor-questionnaire asterisk, but Phase 2 needs to land before the first renewal. Phase 3 is "before first enterprise RFP."

## Phase 1 — Launch blockers (ship before charging anyone)

Ordered by revenue/legal risk descending.

### 1. Stripe webhook endpoint with signature verification and event routing

**Why this is #1:** Checkout exists (`src/app/api/checkout/route.ts`), a setup flow exists (`src/app/setup/page.tsx`), and the proxy enforces access based on `subscriptions.status` (`src/proxy.ts:79`) — but **nothing writes to that `status` column after the initial insert**. There is no webhook handler. The app cannot react to:
- `invoice.payment_failed` → no dunning, paying customers will be locked out the moment their card bounces with no email sent.
- `customer.subscription.deleted` / `updated` → cancellations don't propagate; the customer keeps access after Stripe marks them canceled, OR the Stripe portal change doesn't reach our DB.
- `charge.dispute.created` → no signal to freeze the account.

**Files:**
- Create: `src/app/api/webhooks/stripe/route.ts`
- Create: `src/app/api/webhooks/stripe/__tests__/route.test.ts`
- Migration: `supabase/migrations/20260421_01_stripe_events_idempotency.sql` — table `stripe_event_log(event_id text primary key, received_at timestamptz, processed_at timestamptz, status text)` to deduplicate retries.

**Must handle:**
| Stripe event | DB action |
|---|---|
| `checkout.session.completed` | Same as `setup/page.tsx` idempotent upsert — safer than trusting the query-string landing page. |
| `customer.subscription.updated` | Sync `status`, `plan` (from price ID → plan mapping), `user_limit`, `current_period_end`. |
| `customer.subscription.deleted` | `status = 'canceled'`. |
| `invoice.payment_failed` | `status = 'past_due'`, fire email (see Task 6). |
| `invoice.payment_succeeded` | If previously `past_due`, flip back to `active`. |
| `customer.subscription.trial_will_end` | Fire email 3 days before trial end (pairs with Task 4). |

**Requirements:**
- Verify `Stripe-Signature` with `stripe.webhooks.constructEvent`. **Never parse the raw body as JSON first** — the verifier needs the exact bytes.
- Return 200 within 5s even on DB errors; log and requeue in `stripe_event_log` with `status='retry'` so Stripe's own retry catches up.
- Idempotency: reject any `event.id` already in `stripe_event_log` (Stripe redelivers on 5xx).
- Do NOT leak the signing secret via `console.log`.

**User action after deploy:** Set `STRIPE_WEBHOOK_SECRET` in Vercel. Point the Stripe Dashboard webhook at `https://namihr.com/api/webhooks/stripe` for the 6 events above.

### 2. Harden the `/setup` page against session-ID replay

**Problem:** `src/app/setup/page.tsx:37` calls `stripe.checkout.sessions.retrieve(sessionId)` using a `session_id` from the query string, with no binding to an authenticated user. The session lookup succeeds for *any* paid session belonging to the Stripe account, then mints a `setup_token` that unlocks `workspace_id = NULL` for whoever installs Slack next.

**Attack:** Legit customer A pays. Attacker B (who knows or guesses A's `cs_live_...` ID) visits `/setup?session_id=<A>` **before A clicks "Add to Slack"**, receives the same `setup_token`, installs on B's workspace first. A's payment, B's workspace.

**Why this matters even with unguessable IDs:** The session ID ends up in referers, analytics, browser history, and the Stripe success URL is the same for every plan. It is not treated as a secret by Stripe.

**Fix:**
- Replace the search-param flow with a short-lived HttpOnly cookie set during `/api/checkout` POST that binds the Stripe `session_id` to this browser. `/setup` reads the cookie, not the query string.
- Once consumed (Slack install completes), invalidate the cookie + delete the setup_token.
- Additionally, require `session.customer_email` to equal the email the user entered in the pricing page (carried in the same cookie).

**Files:**
- Modify: `src/app/api/checkout/route.ts` — set HttpOnly `nami_checkout` cookie with `{ sessionId, email }`, SameSite=Lax, Secure, Path=/setup, MaxAge=30m.
- Modify: `src/app/setup/page.tsx` — read cookie instead of `searchParams.session_id`. Reject mismatch.

### 3. Enforce seat limits in the API, not just the billing UI

**Problem:** `src/app/dashboard/settings/billing/page.tsx` displays `user_limit`. Nothing actually blocks new user rows from being created when `count(users) >= subscription.user_limit`. Customers on the Starter plan (50 seats) can add 500 users with zero revenue impact.

**Fix:**
- DB-level: Add a trigger on `users` that refuses INSERT when `count >= user_limit`, returning a Postgres error that bubbles up as a meaningful 4xx. Use `SECURITY DEFINER` so the check reads the subscription row even when the caller's RLS context wouldn't.
- API-level: Every place that creates a user row (Slack OAuth team-import, manual add in the admin UI, CSV import) should catch the error and return a 402 with a message like "Upgrade to add more seats."
- UI-level: Show the seat count / limit in the team import flow. Disable the "Import" button when at limit.

**Files:**
- Migration: `supabase/migrations/20260421_02_seat_limit_trigger.sql`
- Modify: `supabase/functions/slack-oauth/index.ts` — handle the 402 during team import.
- Modify: wherever admin "Import team" exists in `src/app/dashboard/admin/` — propagate the error.

**Gotcha:** Don't count soft-deleted users (see Task 7). Only active users count toward the seat limit.

### 4. Trial start/end fields + trial expiry cron

**Problem:** Landing and pricing pages promise "14-day free trial." There is no `trial_started_at` or `trial_expires_at` column, and no job that flips a trial to expired. Right now the Starter checkout charges on day 0 — which means there **is no trial**, just a free workspace that silently stops existing after Stripe cancels.

**Fix — pick one of two models and commit:**
- **Option A (recommended): Stripe-native trial.** Use `subscription_data.trial_period_days: 14` in the checkout session. Stripe then emits `customer.subscription.trial_will_end` (Task 1 handles it) and auto-charges on day 14. Everything stays in one system.
- **Option B (work):** Local `trial_expires_at` column + cron that emails + locks. Only do this if you want trials without a card on file, which requires a bigger flow change on the pricing page (email capture, no checkout).

Either way, the product must:
- Surface "X days left in trial" in the dashboard top bar (read from `current_period_end` or `trial_end` on the subscription).
- Email at T-3 days (Task 6) and T-0 (card decline or conversion).
- NOT lock out data on day 15 — read-only grace period, then delete after 30 days (see Task 7).

### 5. Observability: Sentry + structured logs in one place

**Problem:** Zero error tracking. The `catch` blocks `console.error` to Vercel logs (ephemeral, per-function) and to Supabase edge logs. There is no way to answer "how many customers hit this error in the last hour" or "show me every error for workspace X." Debugging the first paying customer's bug report will require Vercel log trawling over SSH-adjacent pain.

**Fix:**
- Install `@sentry/nextjs` — wraps server components, API routes, and client errors. Scope-tag events with `workspace_id` and `user_id` (from `getUserWorkspace()`).
- For edge functions (Deno), use `@sentry/deno` — or, pragmatically, a simpler `POST /api/log-error` internal route that Sentry wraps on the Next side. The latter is less ideal but easier to ship.
- PII rules: strip review/feedback text from error payloads (`beforeSend` hook); hash email; never send Slack tokens.

**Non-goals:** No Datadog, no LogRocket, no PostHog — one tool is enough for launch and three is noise.

**User action:** Create a Sentry project, add `NEXT_PUBLIC_SENTRY_DSN` and `SENTRY_DSN` to Vercel.

### 6. Transactional email via Resend

**Problem:** Zero transactional email. Receipts come from Stripe, but nothing else: no trial-expiring warning, no payment-failed notice, no workspace-admin welcome, no account-deletion confirmation. "Slack-only" is fine for in-product messaging but fails the moment a customer's Slack token expires or their workspace uninstalls the app — which is *exactly when* we need to email them.

**Fix:**
- Install `resend`. Use their React Email templates (or plain HTML — keep it minimal).
- Required templates for v1:
  1. **Payment failed** — triggered by Stripe webhook, includes portal link.
  2. **Trial ending in 3 days** — workspace admin.
  3. **Subscription canceled** — confirmation + reactivation link.
  4. **Workspace deletion requested** — confirmation w/ 30-day cancel link (GDPR receipt).
  5. **Workspace deletion completed** — final confirmation, compliance paper trail.
- Put the sender identity under `hello@namihr.com`. Configure SPF + DKIM in DNS before first send.

**What NOT to build now:** Marketing emails, drip sequences, onboarding series. Those belong in Customer.io or similar in month 3+, not here.

**User action:** Resend account, verify sending domain, add `RESEND_API_KEY` to Vercel and Supabase secrets.

### 7. Workspace deletion + 30-day grace (GDPR delivery)

**Problem:** `src/app/privacy/page.tsx:312-317` promises "30-day grace period and permanent deletion" for workspace data. There is no UI, no API, no cron, and no soft-delete column. This is a legal misrepresentation, not just an engineering gap — any EU prospect will ask for the DPA and the GDPR Article 17 workflow, and we can't produce one.

**Fix:**
- Migration: add `workspaces.deleted_at timestamptz NULL`, `workspaces.purge_after timestamptz NULL`. RLS filters `deleted_at IS NULL` on read paths.
- Admin-only UI: `/dashboard/settings/general` — "Delete workspace" button, requires typing workspace name to confirm.
- On click: set `deleted_at = now()`, `purge_after = now() + interval '30 days'`, cancel Stripe subscription, send email (Task 6, template 4).
- Cancel / undo: during the grace period, any admin login restores access and clears the flag.
- Cron: daily job (`supabase/functions/purge-deleted-workspaces`) that hard-deletes workspaces where `purge_after < now()`. Cascade deletes all workspace-scoped tables. Dry-run mode first for the first 2 weeks.
- Receipt: once purged, send template 5 and insert an immutable row into an `audit_log` (migration `20260416_12_audit_log.sql` already exists — reuse it).

**Do not** build per-user self-service deletion for Slack members — they are not the paying customer, and the workspace admin is the data controller. Route individual requests to the workspace admin's settings page.

### 8. Continuous integration: lint + type-check + test on every PR

**Problem:** No `.github/workflows/`. Tests pass locally (87 tests per the SaaS audit), but nothing enforces them. One merged PR that breaks `npx tsc --noEmit` ships to production. One bad migration that breaks RLS goes unnoticed until a customer escalates.

**Fix:**
- Create `.github/workflows/ci.yml`:
  - `npm ci`
  - `npm run lint`
  - `npx tsc --noEmit`
  - `npm test` (Vitest)
  - Fail the PR on any red.
- Branch protection: `main` requires CI green + 1 review.
- Add a separate workflow for Supabase migrations: `supabase db lint` on any file in `supabase/migrations/`.
- Preview deploys on Vercel already exist; add a PR comment with the preview URL (Vercel GitHub app handles this if enabled).

**Non-goal for launch:** E2E tests (Playwright) are valuable but heavy. Ship CI with unit + type + lint gates first; add E2E when the first paying customer has a repeatable flow we care about protecting.

## Phase 2 — Ship within 60 days of first paying customer

### 9. Fire-and-forget the `app_home_opened` handler

**Problem:** `supabase/functions/slack-events/index.ts:209-248` awaits `buildHomeBlocks(appUser)` (which runs 4+ sequential Supabase queries) before returning 200 to Slack. Slack's hard timeout is 3 seconds; at 50+ workspaces this will start missing the window. The DM path at line 268 already uses the correct pattern — mirror it here.

**Fix:** Return 200 immediately. Use `EdgeRuntime.waitUntil()` for the home-tab build. This is a surgical change (~10 lines).

### 10. Alert on cron job failures

**Problem:** `deadline_reminders_cron`, `slack_send_queue_cron`, `cycle-notifications`, `home_tab_refresh_triggers` all log to Supabase function logs on failure. No alert. A broken cron is silent until a customer notices they didn't get a deadline reminder.

**Fix:**
- Wrap each cron body in `try/catch` and `POST` to Sentry (Task 5) on exception with `fingerprint: ["cron", <jobName>]` so Sentry groups by job.
- In Sentry, create an alert rule: "issue with tag `cron` and event count > 3 in 10m → email + Slack channel."

### 11. RLS index audit

**Problem:** The ops audit flagged `EXISTS` subqueries in RLS policies (e.g., `cycle_questions` joining to `performance_cycles` to check `workspace_id`) without confirmed indexes on the join keys. At 100+ workspaces this becomes a sequential scan per row on any unscoped query.

**Fix:**
- Run `EXPLAIN (ANALYZE, BUFFERS)` on the top 10 hottest queries from Supabase's `pg_stat_statements` view.
- For every RLS policy that uses `EXISTS (SELECT 1 FROM parent WHERE parent.id = child.fk AND parent.workspace_id = ...)`, ensure the parent has `(id)` primary key (it does) AND the child has an index on `(fk, workspace_id)` if it is filtered on its own.
- Add `idx_workspaces_team_id` — called out by the ops audit; unindexed today.
- Do NOT preemptively add indexes everywhere. Measure first; indexes have write cost.

### 12. Admin/support impersonation tooling

**Problem:** When a customer emails "my goals page is blank," there is no way to reproduce their view without giving an engineer direct Supabase access. This is both a support velocity problem and a security problem — raw DB access scales badly.

**Fix:**
- New route `src/app/api/admin/impersonate/route.ts`, gated by a `NAMI_STAFF=true` env flag AND a list of allowed `staff_emails` in Supabase. Both checks required.
- Action: generate a short-lived magic-link dashboard session scoped to the target workspace, read-only.
- Every impersonation writes to `audit_log` with `staff_email`, `target_workspace`, `purpose` (freetext justification, required).
- UI: simple `/dashboard/admin/staff` page listing recent workspaces, with a "view as" button that prompts for the justification string.

**What this does NOT do:** Let staff act as a specific user (write access). Read-only is enough for 90% of support calls; write access needs more thought and isn't urgent.

### 13. Rate limit auth endpoints (Phase 1 Task 7 of the old plan)

**Problem:** No rate limiting on `/api/auth/slack-link` or `/api/auth/logout`. Brute-forcing the single-use `dashboard_link_token` is nearly impossible (128 bits of entropy), but `/api/checkout` and `/api/webhooks/stripe` are unlimited — an attacker can hammer checkout to rack up Stripe API cost.

**Fix:** Implement the existing plan's Task 7 verbatim using Upstash. Apply to:
- `/api/auth/slack-link`
- `/api/auth/logout`
- `/api/checkout` (per-IP, 10/min)
- `/api/webhooks/stripe` (per-IP, 60/min — Stripe shouldn't need more; anything faster is abuse)

### 14. Customer-facing data export (GDPR Article 20)

**Problem:** Per-feature CSV exports exist (goals, reviews, surveys, analytics). There is no "download everything" button. GDPR portability says the customer is entitled to a full machine-readable export; delivering that ad-hoc per request does not scale.

**Fix:**
- New endpoint `/api/workspace/export` — admin-only, generates a ZIP of all CSVs the workspace owns (users, goals, reviews, cycles, feedback, etc.).
- Runs as a background job if the workspace is large; emails a signed S3 (or Supabase Storage) URL when done. 7-day expiry on the link.
- Button in `/dashboard/settings/general` → "Export all data."
- Audit-log the request.

### 15. Public status page

**Problem:** When we have an incident (edge function down, Stripe webhook lag, Slack outage affecting us), there is no public signal. Customers email support, support emails engineering, the incident is unmanaged. For a B2B tool this is table stakes.

**Fix:** Use the free tier of Statuspage, BetterStack, or Instatus. Wire uptime checks for:
- `https://namihr.com` (landing)
- `https://namihr.com/dashboard` (200 when unauthenticated redirect is correct)
- Supabase project status (propagate from their API)
- Slack API status (propagate)

Link from the dashboard footer and from `/security`. This is ~1 day of work, almost entirely clicking through the vendor's setup.

## Phase 3 — Before first enterprise RFP / security review

### 16. DPA signing flow

Self-serve DPA on `/dashboard/settings/legal`. Pre-signed by us, countersigned via click-through (or Docusign if enterprise), stored in Supabase Storage with audit trail. Privacy policy already names our sub-processors — the DPA just needs to restate and be signable.

### 17. SOC 2 Type I engagement

Already on the `/security` roadmap. Realistic timeline: 6-9 months to Type I, another 12 months for Type II. Start by picking an auditor (Vanta / Drata / Secureframe handle the grunt work). Until then, keep the `/security` page honest: "SOC 2 Type I in progress, target Q3 2027."

### 18. Data region choice for EU customers

Today everything is in US (Vercel + Supabase US). Some EU customers will block on this. When a deal asks, the answer is "Supabase can host your project in Frankfurt; we'll provision a dedicated instance for your workspace under a separate contract." Don't pre-build multi-region — wait for the first customer who actually needs it and charge for it.

### 19. Changelog page

`/changelog` (Markdown-backed, same pattern as `/content` articles). Post weekly during the first quarter, monthly after. Low lift, high trust signal for buyers. Skip if there is nothing to announce — better silent than stale.

### 20. Complete the Slack integration hardening plan

All 13 tasks in `2026-04-20-slack-integration-hardening.md`, especially Phase 1:
- Token encryption at rest (Vault)
- `event_id` deduplication
- HMAC-signed OAuth state

These are **pre-requisites for SOC 2** and for any security review that asks "are Slack OAuth tokens encrypted at rest." The fact that they aren't today is the single biggest technical gap the security page glosses over.

## Explicitly out of scope

Listed here so they aren't forgotten, and so they aren't re-proposed:

- **Playwright E2E tests.** Real value only after the product flows stabilize; premature today.
- **Multi-region deploy.** Pull-based on first customer demand; don't pre-build.
- **GraphQL or REST public API.** No customer has asked. Every hour spent here is an hour not closing a deal.
- **Mobile app.** Slack IS the mobile app for this product. The dashboard is the ops console.
- **i18n.** All current and target customers are English-first. Revisit at 50+ paying workspaces.
- **Custom SSO (SAML/OIDC beyond Slack).** Slack covers login for 100% of users by design. Add only when a specific enterprise deal blocks on it, and charge for it.
